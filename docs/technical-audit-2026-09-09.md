# Технический аудит schupy.ru

**Дата:** 9 сентября 2026 г.  
**Объект:** репозиторий `robot-satellite`, production-сборка Next.js 15.5.14  
**Объём:** архитектура, безопасность, надёжность, производительность, SEO, доступность, данные и CI/CD.

## Резюме

> **Статус реализации (обновлено 9 сентября 2026 г.).** В следующем коммите закрыты или существенно снижены риски Issues 1–4, 6–9, 14 и 16: зависимости обновлены и audit очищен, API заявок валидируется и ограничивается, поиск лимитирован и отменяет устаревшие запросы, CI выполняет quality checks, добавлены security headers, согласие и политика, исправлены RSS defaults и sitemap, конфигурация SMTP документирована. Issues 5, 10–13 и 15 остаются частично или полностью открыты и требуют инфраструктурных/контентных работ.

Сборка и TypeScript-проверка проходят, 703 контентные страницы успешно пререндерятся (578 товаров и 125 статей). При этом перед развитием сайта рекомендуется закрыть четыре блокирующих риска:

1. production-зависимости содержат 18 известных уязвимостей, включая одну critical;
2. публичный endpoint заявок не имеет серверной валидации, лимитов или антиспама;
3. поиск возвращает неограниченный ответ (113 КБ для одного обычного запроса) и допускает дешёвую нагрузку на сервер;
4. сборка намеренно пропускает lint, а deploy выполняется без тестов, health check и автоматического rollback.

Ниже каждый пункт оформлен как самостоятельная GitHub issue: заголовок, приоритет, доказательство, влияние, план и критерии приёмки можно копировать без доработки.

## Issue 1 — Обновить уязвимые production-зависимости

**Приоритет:** P0  
**Метки:** `security`, `dependencies`, `critical`

### Доказательство

`npm audit --omit=dev` обнаруживает **18 уязвимостей: 1 low, 2 moderate, 14 high, 1 critical**. Затронуты, среди прочего, `next`, `nodemailer`, `sharp`, `postcss`, `undici`, `ws`, `js-yaml` и цепочка Puppeteer. Версии Next.js и Nodemailer закреплены в production dependencies.

### Риск

В зависимости от достижимости конкретного кода возможны DoS, cache poisoning, XSS, SSRF, обход проверок и инъекция почтовых заголовков. Нельзя считать транзитивную уязвимость эксплуатируемой автоматически, но critical/high findings требуют разбора и обновления.

### План исправления

1. Обновить Next.js, Nodemailer и остальные direct dependencies до исправленных совместимых версий.
2. Удалить `puppeteer` из production dependencies либо перенести в `devDependencies`, если он используется только локальным SEO-скриптом.
3. Выполнить `npm audit fix` без `--force`, затем отдельно проверить breaking upgrades.
4. Добавить Dependabot/Renovate и audit-шаг в CI.

### Критерии приёмки

- `npm audit --omit=dev` не сообщает critical/high findings либо для каждого принятого исключения есть документированная достижимость, владелец и срок пересмотра.
- `npm run build` и smoke-тест ключевых страниц проходят после обновления.
- Puppeteer не попадает в production bundle без runtime-необходимости.

## Issue 2 — Защитить `/api/contact` от спама, DoS и некорректного ввода

**Приоритет:** P0  
**Метки:** `security`, `backend`, `forms`

### Доказательство

Endpoint принимает произвольный JSON без проверки Content-Type, схемы, длины полей, email/телефона и origin. Нет rate limiting, CAPTCHA/honeypot и идемпотентности. Пользователь полностью контролирует `subject`, `replyTo`, текст и `cart_json`; запрос сразу инициирует SMTP-отправку. Парсинг JSON находится вне обработчика ошибок. При выключенном SMTP любой запрос возвращает 500 и раскрывает имя отсутствующей переменной окружения.

### Риск

Злоумышленник может массово отправлять почту через сервер, исчерпать SMTP-квоту/ресурсы, внедрять нежелательные данные в заголовок темы и отправлять очень большие payload. Ошибки конфигурации и библиотеки раскрываются клиенту.

### План исправления

1. Валидировать тело на сервере (например, Zod): допустимые поля, форматы и жёсткие максимальные длины; тему формировать только сервером из enum контекста.
2. Ограничить размер request body на reverse proxy и в приложении; возвращать 400/413/415 вместо 500.
3. Добавить rate limit по IP + глобальный лимит, honeypot или Turnstile и защиту повторной отправки.
4. Проверять same-origin как дополнительный сигнал (не как единственную защиту).
5. Логировать correlation ID и внутреннюю ошибку на сервере; клиенту возвращать нейтральный код ошибки.
6. Добавить timeout SMTP и тесты негативных сценариев.

### Критерии приёмки

- Невалидный JSON/Content-Type/поля получают 4xx; oversized payload — 413.
- Лимит запросов проверяется автоматическим тестом и возвращает 429.
- Клиент не может задать произвольную тему письма или получить текст внутренней ошибки.
- Unit/integration tests покрывают валидную отправку, SMTP failure, malformed JSON, rate limit и honeypot.

## Issue 3 — Ограничить и кэшировать результаты `/api/search`

**Приоритет:** P1  
**Метки:** `performance`, `backend`, `security`

### Доказательство

Поиск синхронно проходит по всем 578 товарам и возвращает **все** совпадения. Запрос `q=щуп` локально вернул HTTP 200 с телом **113 159 байт**, хотя UI использует только первые 6 результатов. Endpoint не задаёт limit, cache headers или rate limit.

### Риск

Каждое нажатие пользователя создаёт лишний CPU/network расход; параллельные запросы легко усиливают нагрузку. По мере роста каталога задержка и объём ответа растут линейно.

### План исправления

1. Добавить `limit` с серверным максимумом (например, 10) и возвращать отдельно `total`.
2. Прекращать накопление детальных результатов после лимита, сохранив дешёвый подсчёт либо отказавшись от точного total.
3. Ограничить длину `q`, нормализовать Unicode и отклонять недопустимые запросы.
4. Добавить abort предыдущего fetch в `SearchBar`, чтобы старый ответ не перезаписал новый.
5. Задать безопасное краткосрочное кэширование и rate limit; измерить p95.

### Критерии приёмки

- API никогда не возвращает больше серверного лимита.
- Ответ типичного запроса меньше 10 КБ, а p95 зафиксирован нагрузочным тестом.
- Быстрый ввод не показывает результат устаревшего запроса.
- Есть тесты ранжирования, лимитов и Unicode/длинных запросов.

## Issue 4 — Сделать CI обязательным и исправить lint-команду

**Приоритет:** P1  
**Метки:** `ci`, `quality`, `testing`

### Доказательство

Workflow запускает только `npm ci` и `npm run build`. В `next.config.ts` включено `eslint.ignoreDuringBuilds: true`. `npm run lint` использует устаревший `next lint`; команда проходит только с тремя предупреждениями о `<img>`. Автоматических тестов и test script нет. Кроме того, `eslint-config-next` (15.2.3) не синхронизирован с `next` (15.5.14).

### Риск

В main можно доставить lint-регрессию и функциональную поломку. Единственный workflow сразу разворачивает commit после build, не отделяя проверку от деплоя.

### План исправления

1. Мигрировать на ESLint CLI и синхронизировать версии Next.js/eslint-config-next.
2. Добавить scripts: `typecheck`, `test`, `test:e2e` и CI job для PR/push.
3. Убрать `ignoreDuringBuilds` после устранения предупреждений.
4. Сделать deploy зависимым от успешного quality job и включить branch protection.

### Критерии приёмки

- PR обязательно запускает lint, typecheck, unit/integration tests и production build.
- Предупреждения ESLint либо исправлены, либо точечно обоснованы.
- Deploy не запускается при падении любой обязательной проверки.

## Issue 5 — Добавить health check, rollback и сериализацию deploy

**Приоритет:** P1  
**Метки:** `devops`, `reliability`

### Доказательство

Deploy переключает `current` symlink до проверки работоспособности, затем выполняет `pm2 restart ... || pm2 start ...`. Нет `concurrency`, health check новой версии, rollback, таймаута SSH и проверки свободного места. Одновременные push могут конкурировать за symlink и очистку releases.

### Риск

Успешно собранный, но не запускающийся release немедленно становится production. Конкурирующие workflow могут развернуть не тот commit или удалить нужный release.

### План исправления

1. Добавить GitHub Actions `concurrency` на production environment.
2. Запускать новый release на отдельном порту/процессе, проверять `/api/health` и только затем атомарно переключать symlink.
3. При неуспешном health check сохранять предыдущий symlink и завершать job ошибкой.
4. Добавить SSH connect timeout, явный `set -euo pipefail`, deployment metadata и smoke-тест публичного URL.

### Критерии приёмки

- Искусственно сломанный startup не меняет рабочую версию.
- Два параллельных deploy сериализуются/отменяются предсказуемо.
- Rollback на предыдущий release документирован и проверен.

## Issue 6 — Настроить HTTP security headers и скрыть fingerprint

**Приоритет:** P1  
**Метки:** `security`, `headers`

### Доказательство

Локальный production server отдаёт `X-Powered-By: Next.js`; отсутствуют Content-Security-Policy, HSTS, `X-Content-Type-Options`, `Referrer-Policy` и `Permissions-Policy`. Страница исполняет inline Yandex Metrika script, что потребует nonce/hash или отдельной стратегии CSP.

### Риск

Нет дополнительной защиты от XSS/clickjacking/MIME sniffing и нежелательного доступа к browser capabilities. Заголовок раскрывает технологию.

### План исправления

1. Включить `poweredByHeader: false`.
2. Настроить headers в Next/reverse proxy: CSP (с nonce), HSTS только на HTTPS, `nosniff`, строгий referrer policy, permissions policy и frame-ancestors.
3. Сначала запустить CSP Report-Only, собрать нарушения, затем включить enforcement.

### Критерии приёмки

- Автотест headers проверяет homepage и API.
- CSP не содержит `unsafe-eval`; inline scripts разрешаются nonce/hash.
- SecurityHeaders/аналогичный скан не показывает high-risk omissions.

## Issue 7 — Добавить согласие на обработку персональных данных и управление аналитикой

**Приоритет:** P1  
**Метки:** `legal`, `privacy`, `forms`

### Доказательство

Формы собирают имя, компанию, email, телефон и сообщение, но рядом нет ссылки на политику и явного согласия. В layout безусловно загружается Яндекс Метрика с Webvisor. В навигации отсутствует страница политики/управление аналитическими cookies.

### Риск

Пользователь не информирован о целях, сроках и получателях обработки данных и не может управлять необязательной аналитикой. Конкретные юридические требования нужно подтвердить с профильным юристом для фактической юрисдикции и инфраструктуры.

### План исправления

1. Подготовить и опубликовать политику конфиденциальности/обработки ПДн.
2. Добавить обязательный consent checkbox во все формы с версией согласия и ссылкой.
3. Загружать необязательную аналитику согласно утверждённой consent-модели; предоставить отзыв выбора.
4. Задокументировать сроки хранения и доступ к SMTP/Метрике.

### Критерии приёмки

- Без обязательного согласия форма не отправляется.
- Политика доступна из каждой формы и footer.
- Поведение Метрики соответствует письменному заключению юриста и проверяется E2E-тестом.

## Issue 8 — Исправить метаданные RSS и исключить generated artifact drift

**Приоритет:** P2  
**Метки:** `seo`, `content`, `build`

### Доказательство

При локальной production-сборке `public/rss.xml` генерируется с placeholder-значениями `Название сайта` и `https://ваш-домен.ru`. Файл отслеживается Git и меняется во время build, поэтому содержимое зависит от окружения и может устаревать. Статический `public/robots.txt` также дублирует динамический `src/app/robots.ts`.

### Риск

Локальные/preview сборки публикуют неверные canonical RSS links и бренд; два источника robots создают риск расхождения. Build с изменением tracked-файла не воспроизводим.

### План исправления

1. Генерировать RSS через route handler на основе единого validated site config либо писать artifact только в build output.
2. Заменить placeholder defaults на production-safe значения и падать в CI при некорректном URL.
3. Оставить ровно один источник robots.
4. Добавить XML/URL тест RSS и sitemap.

### Критерии приёмки

- `npm run build` не изменяет tracked files (`git diff --exit-code`).
- RSS title/link/atom link корректны во всех окружениях.
- Robots и sitemap указывают на один валидный canonical host.

## Issue 9 — Исправить sitemap: реальные даты и отсутствующий маршрут `/podbor`

**Приоритет:** P2  
**Метки:** `seo`

### Доказательство

Sitemap ставит `new Date()` как `lastModified` для всех статических страниц и всех 578 товаров на каждом build. Маршрут `/podbor`, присутствующий в основной навигации, в staticRoutes отсутствует. Для товаров нет поля даты изменения.

### Риск

Поисковики получают ложный сигнал массового обновления каталога при каждом deploy, а важная conversion page не заявлена в sitemap.

### План исправления

1. Добавить `updatedAt` в данные товара или получать mtime из контролируемого источника.
2. Для редко меняющихся страниц использовать фактическую дату изменения или не указывать поле.
3. Добавить `/podbor`; проверить полноту индексируемых canonical routes.

### Критерии приёмки

- Два build без изменения контента дают одинаковые `lastModified`.
- `/podbor` присутствует в sitemap.
- Автотест сравнивает sitemap с ожидаемым набором routes и исключает 404.

## Issue 10 — Устранить дубли артикулов и формализовать схему контента

**Приоритет:** P2  
**Метки:** `data-quality`, `catalog`

### Доказательство

В 578 JSON-файлах обнаружены 5 групп повторяющихся артикулов: `3419825100`, `A-2008-0368`, `A-4038-0001`, `A-2197-0049`, `A-4071-2001` (часть повторяется трижды). Runtime приводит данные через TypeScript cast, но не валидирует обязательные поля и типы. 318 итоговых product title превышают 60 символов.

### Риск

Поиск показывает несколько внешне одинаковых позиций; менеджер или клиент может выбрать неверную карточку. Некорректный JSON способен уронить весь build. Длинные titles могут обрезаться в поисковой выдаче.

### План исправления

1. Провести бизнес-разбор дублей: объединить карточки или явно различить вариант/состояние/комплектность.
2. Добавить JSON Schema/Zod validation и отдельный `validate:content`.
3. Проверять уникальность slug и согласованную уникальность `(article, variant)`.
4. Ввести SEO-пределы и отчёт, не обрезая автоматически важные артикулы.

### Критерии приёмки

- Для каждой группы дублей принято и реализовано решение.
- CI падает на malformed data, duplicate slug и неоднозначном business key.
- Отчёт проверяет длины title/description и обязательные изображения/specs.

## Issue 11 — Исправить доступность поиска, меню, корзины и форм

**Приоритет:** P2  
**Метки:** `accessibility`, `frontend`

### Доказательство

Autocomplete визуально поддерживает стрелки, но input не имеет роли combobox, `aria-expanded`, `aria-controls` и `aria-activedescendant`; список не размечен как listbox/options. Кнопка мобильного меню всегда имеет текст «Открыть меню», не сообщает expanded state. Кнопка удаления в корзине отображает только `X` без доступного названия товара. Поля формы корзины используют placeholder вместо label; ошибки RFQ не связаны с inputs через `aria-describedby` и не объявляются live-region.

### Риск

Клавиатурные и screen-reader пользователи не получают состояние компонентов, назначение контролов и сообщения об ошибках. Это повышает вероятность брошенной заявки.

### План исправления

1. Реализовать WAI-ARIA combobox pattern и объявление количества результатов.
2. Добавить `aria-expanded`/`aria-controls` меню, закрытие по Escape и возврат фокуса.
3. Добавить явные label/autocomplete/inputMode, доступные имена кнопок и live regions.
4. Добавить axe + keyboard E2E tests; вручную проверить NVDA/VoiceOver.

### Критерии приёмки

- axe не находит serious/critical violations на home/catalog/product/cart/contact.
- Все сценарии доступны только с клавиатуры с видимым focus.
- Ошибки и успешная отправка объявляются screen reader.

## Issue 12 — Оптимизировать изображения и убрать необоснованный `unoptimized`

**Приоритет:** P2  
**Метки:** `performance`, `frontend`

### Доказательство

ESLint отмечает три использования raw `<img>`. Для внешних S3-изображений компоненты передают `unoptimized`, хотя hostname уже разрешён в `next.config.ts`; это исключает resize/format optimization. Внешние картинки составляют ключевой визуальный контент каталога и статей.

### Риск

Пользователь скачивает изображения больше требуемого viewport, что ухудшает LCP и расход мобильного трафика. Raw images также труднее защищать единообразными dimensions/fallback policy.

### План исправления

1. Проверить CORS/форматы S3 и включить Next Image optimization или image CDN loader.
2. Перевести logo/blog/noscript там, где уместно, на согласованную стратегию; tracking pixel можно точечно исключить с комментарием.
3. Указать корректные `sizes`, width/height и cache TTL.
4. Снять Lighthouse/Web Vitals baseline и сравнить после изменения.

### Критерии приёмки

- Нет необоснованных `no-img-element` warnings.
- Product/blog images отдаются в размере и формате, соответствующих viewport.
- LCP и transferred image bytes не ухудшились относительно зафиксированного baseline.

## Issue 13 — Добавить наблюдаемость для заявок и runtime-ошибок

**Приоритет:** P2  
**Метки:** `observability`, `reliability`

### Доказательство

Ошибка SMTP только преобразуется в JSON; структурированного server logging, request ID, метрик latency/success rate и alert нет. Клиент показывает общий текст, поэтому факт потери заявки можно не заметить. Health endpoint отсутствует.

### Риск

Отказ SMTP, рост 5xx или деградация поиска обнаружатся по жалобе клиента, а связать событие с логами и deploy будет сложно.

### План исправления

1. Ввести структурированные логи без PII, correlation/request ID и release SHA.
2. Добавить метрики заявок (attempt/success/failure/latency), API 4xx/5xx и alert по SLO.
3. Добавить liveness/readiness endpoint, проверяющий процесс без отправки тестового письма.

## Issue 14 — Устранить гонку ответов autocomplete и добавить AbortController

**Приоритет:** P2  
**Метки:** `bug`, `search`, `frontend`

### Доказательство

Debounce отменяет только ещё не запущенный timeout. Уже отправленный `fetch` не отменяется и не сверяется с актуальным query. Более медленный ответ на старый запрос может прийти после нового и заменить результаты.

### Риск

Пользователь видит товары не по текущему тексту и может перейти в неверную карточку; параллельные запросы создают лишнюю нагрузку.

### План исправления

Использовать AbortController на каждый effect, отменять fetch в cleanup и игнорировать AbortError. Дополнительно сверять response query/request sequence перед обновлением state.

### Критерии приёмки

- Тест с искусственно переставленными задержками всегда показывает результаты последнего query.
- Предыдущий network request получает aborted status при новом вводе/unmount.

## Issue 15 — Исправить SEO pagination и canonical для query-страниц

**Приоритет:** P3  
**Метки:** `seo`, `frontend`

### Доказательство

Страницы `/blog?page=N` используют одинаковые статические title/description и не объявляют canonical. `/catalog?search=...` и `/catalog?category=...` также доступны как server-rendered варианты без явной canonical/noindex стратегии.

### Риск

Поисковый индекс может содержать дублирующиеся/малополезные parameter URLs, а сигналы ссылок распределяются между вариантами.

### План исправления

1. Согласовать индексируемость pagination, filters и internal search.
2. Генерировать metadata по searchParams: canonical, robots и уникальный pagination title.
3. Internal search обычно закрыть `noindex,follow`; category pages либо сделать полноценными landing pages, либо canonical на каталог.

### Критерии приёмки

- Для каждой query-комбинации документирована и протестирована canonical/robots стратегия.
- URL внутреннего поиска не попадают в sitemap и получают ожидаемый noindex.

## Issue 16 — Сделать конфигурацию окружения типизированной и fail-fast

**Приоритет:** P3  
**Метки:** `configuration`, `reliability`

### Доказательство

Значения site/S3 URL имеют fallback в нескольких файлах, SMTP host/port зашиты в код, а `.env.example` не перечисляет `SMTP_USER`, `SMTP_PASSWORD`, `CONTACT_TO`. В репозитории и workflow присутствует публичный, судя по названию, Web3Forms key, хотя текущая форма отправляет через внутренний API и ключ не использует.

### Риск

Неполное окружение обнаруживается после запуска либо создаёт artifacts с placeholder URL. Неиспользуемый credential затрудняет понимание attack surface и ротацию.

### План исправления

1. Создать единую server/client env schema и проверять её на build/start.
2. Дополнить `.env.example` всеми переменными без реальных секретов.
3. Удалить/отозвать неиспользуемый Web3Forms key; секреты хранить только в environment secrets.
4. Централизовать canonical site config.

### Критерии приёмки

- Некорректная обязательная конфигурация останавливает build/start с понятной ошибкой.
- В tracked files нет действующих credentials.
- README описывает локальное, preview и production окружение.
